# `voiage` Integration Strategy

## Context

`lifecourse` is the disease and policy microsimulation package. It generates
scenario, PSA, budget impact, equity, and economic evaluation outputs.

`voiage` is a separate Value of Information library. It provides EVPI, EVPPI,
EVSI, ENBS, plotting, CLI workflows, and advanced VOI method scaffolds.

The projects should work together through a narrow analysis contract rather than
by merging responsibilities.

The broader artifact approach is documented in
`docs/interchange/model_interchange_strategy.md`.

The provisional shared artifact profile is HEOML, currently embedded under
`heoml/`.
`voiage` should treat that profile as the shared run-bundle contract for
lifecourse-compatible VOI handoff, not as a replacement for `voiage`'s own
result schemas.

## Recommended Boundary

- `lifecourse` owns model configuration, simulation engines, cohorts, genomic
  testing pathways, parameter provenance, calibration/validation targets, and
  reproducible run bundles.
- `voiage` owns VOI algorithms, VOI-specific schemas, metamodel choices, study
  design evaluation, VOI plots, and VOI method validation.
- The integration boundary should be net-benefit and parameter-sample artifacts,
  not internal simulation objects.

## Preferred Integration Path

1. `lifecourse` exports PSA net-benefit arrays, strategy names, parameter
   samples, willingness-to-pay thresholds, population scaling metadata, time
   horizon, discount rate, and run provenance.
2. A thin `lifecourse` adapter converts those artifacts into `voiage.ValueArray`
   and `voiage.ParameterSet` objects when the optional `voiage` extra is
   installed.
3. `voiage` computes EVPI, EVPPI, EVSI, ENBS, and VOI plots.
4. `lifecourse` stores VOI outputs in its reproducible reporting bundle with
   provenance pointing to the `voiage` version and method settings.

## Dependency Policy

`voiage` should not become a core `lifecourse` dependency. Its current
dependency set is heavier than the base `lifecourse` runtime because it includes
JAX, NumPyro, scikit-learn, statsmodels, xarray, plotting, and CLI tooling.

The recommended package shape is:

- `lifecourse[voi]`: optional integration extra that depends on a stable
  `voiage` release.
- `voiage` core: minimal EVPI/EVPPI data structures and NumPy-based methods.
- `voiage[jax]`: JAX/NumPyro acceleration and Bayesian methods.
- `voiage[metamodels]`: scikit-learn/statsmodels regression methods.
- `voiage[plotting]`: plotting dependencies.
- `voiage[cli]`: CLI dependencies if they are not needed by the library API.
- `voiage[dev]`: tests, docs, mutation, profiling, and release tooling.

If `voiage` keeps all advanced dependencies in its default install, `lifecourse`
should integrate through optional subprocess/CLI or artifact exchange first and
avoid importing `voiage` in production code paths.

Pickle should not be used for the integration contract. It is Python-specific,
unsafe for untrusted inputs, and not usable by future R, Julia, Go, Rust,
TypeScript, or C# consumers.

## API Contract Needed From `voiage`

The integration needs a small, stable public surface:

- `voiage.ValueArray.from_numpy(values, strategy_names=...)`
- `voiage.ParameterSet.from_numpy_or_dict(...)`
- `voiage.evpi(...)`
- `voiage.evppi(...)`
- `voiage.evsi(...)`
- `voiage.enbs(...)`
- clear method settings for EVSI approximations
- stable result objects or dictionaries with method name, inputs, assumptions,
  scaling metadata, and diagnostics

`lifecourse` should not depend on experimental `voiage` internals, advanced
backend classes, notebooks, or CLI parsing.

## Work Needed In `lifecourse`

- Add a `voiage` optional extra only after a stable dependency target is chosen.
- Add artifact exporters for PSA net benefits and parameter samples.
- Add adapter tests with a small fixture and optional import handling.
- Add backend selection such as `voi_backend="internal"` and
  `voi_backend="voiage"`.
- Keep existing internal VOI calculations as fallback until parity is proven.
- Store `voiage` method settings and version in run manifests.

## Work Needed In `voiage`

- Split default dependencies so core EVPI/EVPPI does not force JAX/NumPyro and
  other heavy method dependencies unless needed.
- Align package metadata and classifiers with the declared license.
- Provide stable schema/result objects for integration consumers.
- Add a compatibility fixture that can be generated by `lifecourse` and consumed
  by `voiage`.
- Add a documented health-economics adapter example using net benefits,
  parameter samples, strategy names, population, horizon, and discount rate.
- Maintain semantic versioning and compatibility notes for the public VOI API.

## Promotion Criteria

Promote `voiage` integration from experimental to supported only when:

- `lifecourse` and `voiage` agree on artifact schemas.
- EVPI/EVPPI/EVSI fixture results match within documented tolerance.
- dependency extras avoid bloating the default `lifecourse` install.
- CI smoke checks cover the optional integration.
- docs explain method assumptions, limitations, and version provenance.

## Non-Goals

- Do not merge the repositories.
- Do not make `lifecourse` depend on `voiage` for base simulation runs.
- Do not rewrite `lifecourse` VOI output paths before parity is proven.
- Do not expose `voiage` experimental methods as production `lifecourse`
  features without validation and support ownership.
